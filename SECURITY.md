# Security status — stabilization review

Container runtime isolation remains a development preview pending acceptance on the actual Debian host. Native mode is a per-application proxy manager, not a network sandbox.

## Repository audit

Local history contains `workspace-settings.json`, introduced in `bab0e22` (v0.9.1). No `workspace.json` path appears in available history. The tracked file is generated by setup and contains local installation choices. Its presence resulted from a missing root `.gitignore`; `docker/.gitignore` protected only `docker/xray`. The reason someone chose to stage the file, or its publication on GitHub, cannot be established from this checkout alone.

Root exclusions now cover workspace settings, environment secrets, authentication/configuration directories, state/runtime files, private keys, Python caches, logs, backups, and staged binaries. Docker and Podman contexts use explicit file allowlists. Tracking removal preserves the existing local settings file, including its uncommitted changes. No history is rewritten. A path-only credential-pattern scan of tracked HEAD files found no matches for common private-key, AWS access-key, GitHub-token, or OpenAI-key formats; this does not prove the absence of every secret, especially in old commits or remote copies.

If an owner discovers actual credentials in history, assess exposure and approve rotation/removal separately. Ignore rules and a tracking-removal commit cannot revoke credentials or erase existing clones.

## Runtime trust

The guard refuses missing container markers, missing/invalid host namespace fingerprints, shared host networking, missing network interfaces, and missing netfilter tools. Both IPv4 and IPv6 OUTPUT DROP policies precede any exceptions. Bootstrap failures identify a fixed stage and stop before any agent shell starts. An installed marker is diagnostic only; subsequent verification still queries both families and performs unprivileged direct-connect probes.

The manager UID is trusted to reach upstream networks; the separate agent UID is not. The agent home and manager configuration are restricted to mode 0700. New state/authentication files inherit a restrictive umask. Existing contents are not recursively chmodded/chowned, and `/workspace` ownership is never changed. Volumes are not encrypted. The host owner, root, container engine administrators, proxy provider, image supply chain, and trusted manager process remain outside this boundary. Agent tools necessarily access their own authentication and all mounted projects.

Native session-safe Fastest uses only RoutingService over a filesystem Unix socket inside the user-private configuration directory. It never exposes an unauthenticated TCP management API. All candidate outbounds remain installed so existing connections can finish. The default outbound is blackhole; no direct outbound is synthesized. Legacy or changed configurations defer automatic changes instead of restarting sessions.

Caveman is optional and fetched from an explicit release tag at build time. Tags and base-image tags are not immutable supply-chain verification. The upstream installer is never executed. No third-party SessionStart hook is created or enabled. Existing legacy hooks/defaults are reported and preserved for owner review.

## Startup filesystem correction

Guard success followed by failure creating `/home/khroxy` identifies a subsequent filesystem bootstrap failure; it does not establish a firewall verification failure or prove live isolation. The old startup assumed UID 0 could traverse another user's private home despite dropping DAC-bypass capabilities. The image now explicitly precreates `/home/khroxy` and `.config` with traversable mode 0755 on the read-only image. The mounted credential directory remains private, mode 0700, owned by manager UID/GID 12000.

Bootstrap does not create image home directories. It adjusts only the two existing volume-root owners, then validates writes as their owning UIDs and validates tmpfs/project access. It never recursively changes persisted files, applies Podman's `:U`, changes volume names/targets, or changes project ownership. Root filesystem read-only status and all dedicated writable mounts are checked from mount metadata. Only fresh temporary files in the runtime homes and `/tmp` are created and removed; project access is inspected without writes.

Startup readiness is a separate root-owned `/run/khroxy-startup-ready` marker. The verifier checks process state and this marker before checking the existing guard marker, both firewall families, and unprivileged bypass probes. Process exit before/during verification is reported separately from an actual verification failure. No capability or network exception was added. See [startup follow-up review](STARTUP_FIX_REVIEW.md).

## Required Debian acceptance

Use a disposable test project and separately approved container start. Record engine/version, rootless status, networking backend, Xray version, and kernel/netfilter support. Never run `network-guard.sh` on the host.

1. Verify private namespace fingerprints, startup guard stage, bootstrap and exec capabilities, and IPv4/IPv6 OUTPUT DROP policies inside the container.
2. Inspect owner/conntrack/loopback rules and confirm the unprivileged agent lacks NET_ADMIN and cannot become the manager/root user.
3. Demonstrate successful proxied traffic through an approved profile. Demonstrate blocked direct IPv4/IPv6 TCP, UDP, DNS TCP/UDP, alternate resolver, host-gateway, and LAN attempts. A system with no IPv6 route cannot independently prove an IPv6 firewall block.
4. Confirm the published proxy listens only on host 127.0.0.1 and cannot be reached from another host or unintended containers.
5. Stop/kill Xray and repeat bypass attempts; verify startup failure stops access. Check both rootless pasta and Docker bridge separately.
6. Check UID mappings, project write access, volume permissions, login/settings persistence, and rebuild/recreation with existing volumes. Verify no host credential or engine socket mounts.
7. Verify native user services across login/reboot as configured, real profile health transitions, API compatibility, and a long application session during automatic switching.

If kernel modules, rootless permissions, pasta behavior, or other host configuration prevents installation/query of either firewall family, stop for owner review. Do not add privileged mode, host networking, disable IPv6, remove checks, or modify host firewall/SSH to make acceptance pass.
